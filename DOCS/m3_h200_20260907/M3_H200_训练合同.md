# M3 在 H200 上的对照训练合同

目标是对齐 L40S M1 的优化与数据协议，在 H200 上从第 1 轮训练 M3。M3 的精度和速度尚须正式运行验证。L40S 的 `scratch` 目录名不代表随机初始化：现场原始日志确认加载了 FCOS3D 预训练，因此本次也加载同一预训练文件，不从当前 M1 checkpoint 接续。

| 项目 | L40S 实际运行 | H200 M3 正式协议 |
|---|---|---|
| GPU / 物理 batch | 4 × 1 | 2 × 1，累积 2 个微步 |
| 有效全局 batch | 4 | 4 |
| 每轮更新 / 总轮数 | 5,983 / 24 | 5,983 / 24，共 143,592 次更新 |
| 每轮日志步数 | 5,983 次 | 11,966 个微步；每 2 微步执行一次更新 |
| 优化器 | AdamW，LR 1e-4，weight decay 0.01 | 相同；backbone LR 为主 LR 的 0.1 |
| 梯度裁剪 | L2 norm，max norm 35 | 所有微步汇总后只裁剪一次，再更新 |
| LR 调度 | 按 epoch 的 cosine，min ratio 0.001 | 相同；线性 warmup 仍为 500 次优化器更新，ratio 1/3 |
| 精度 | FP32 张量；允许 matmul/cuDNN TF32 | 显式设置相同；不启用 AMP / BF16 |
| 初始化 | FCOS3D R101 预训练 | 同一文件，225,215,819 bytes；`resume_from=None` |
| 图像与时域 | 训练 resize=[720]，随机翻转与颜色增强；历史 2 帧，未来 4 帧 | 相同，并保留 future-metadata-only 输入优化 |
| Backbone | frozen_stages=1，norm_eval=True，BN 参数冻结 | 相同 |
| 数据 / workers | 同一训练划分，2 workers/rank | 相同训练划分，2 workers/rank |
| seed / 验证 | seed=0，deterministic；训练中不验证 | 相同；启动须带 `--seed 0 --deterministic --no-validate` |
| checkpoint / 日志 | 每轮完整保存；日志间隔 10 次更新 | 每轮完整保存；日志间隔 20 微步，即 10 次更新 |

物理 batch 不能直接改为 2：占据损失中的比例项和 Lovasz 在 batch 内聚合，M3 NLL 又按留出回波数归一化，直接合 batch 会改变单样本损失的权重。原相机翻转和空间注意力还存在读取第一个样本信息的路径。因此用虚拟四 rank sampler 和梯度累积保留单样本 forward，令同一次更新接收原四 rank 的样本索引、分组和 padding。

M3 仍使用每雷达 **1 sweep、最大回波年龄 0.15 秒**，M1 使用 5 sweeps。这是已设计的方法差异，不能为了“参数等价”悄悄改变。后验更新、留出 NLL、概率特征迁移也是方法差异；若要把结果严格归因于后验迁移，后续还需同为 1 sweep 的 M1 对照。未来 ego transform/action 仍为给定条件。不同 PyTorch/CUDA、物理 rank 和 worker RNG 分配不构成逐位复现；代码测试验证采样和优化器更新语义，真实跨软件栈效果以实测为准。

## 配置入口与执行

模板：`projects/configs/radarflowocc/action_condition_GMO_radar_m3_h200_equivalent.py`。依据副本：`DOCS/m3_h200_20260907/l40s_resolved_reference.py`。生成器将实际 L40S 的共享模型、图像 pipeline、优化器参数复制到 M3，并覆盖明确列出的 M3 方法字段；若参考预算不符则报错。历史 snapshot 中的 `epoch_12.pth` resume 路径不会带入正式 M3。

在已验证的 H200 环境、代码根目录运行以下命令，只生成配置与必要数据链接，不启动训练：

```bash
python tools/m3_prepare_h200_config.py --create-data-links
```

默认生成 `configs_runtime/m3_h200_equivalent.py`。所有输入均可通过 `--data-root`、`--occ-root`、`--pretrained`、`--work-dir`、`--output`、`--reference-config` 覆盖，或使用对应 `M3_DATA_ROOT`、`M3_OCC_ROOT`、`M3_PRETRAINED`、`M3_WORK_DIR`、`M3_OUTPUT`、`M3_L40S_REFERENCE_CONFIG` 环境变量。若输出配置已存在，或工作目录非空，生成器拒绝覆盖。

首次预检可以不绑定缓存。`tools/m3_build_observation_cache.py` 完成独立 M3 缓存构建后，正式配置生成时加 `--radar-cache /实际/M3缓存路径`，或设置 `M3_RADAR_CACHE`。生成器只读取 `build_status.json`：状态须为 `COMPLETE`，覆盖 train、val，且 `tokens_processed == tokens_required > 0`；再以生产 `NuScenesRadarObservations.manifest` 逐一匹配当前 train/val/test 的完整配置，不重复维护另一套 schema。所有检查通过才将三个 split 绑定为 readonly；未完成、有限 smoke、旧 M1 栅格或任意 manifest 不匹配都会拒绝。

此绑定过程不加载 nuScenes 数据库、不遍历原始图像/PCD/NPZ、不做哈希扫描。每个 NPZ 在训练读取时仍执行生产 loader 的 token、schema、形状和值检查；缺失或损坏条目会直接报错，不回退到临时构建。配置协议状态标为 `HOST_RUNTIME_GPU_SMOKE`，表示进入宿主机新环境的 GPU 验证阶段，而非宣称正式训练已启动。

缓存构建器支持 `--workers 1–8`，默认 1；已先采用 4 workers，2026-09-07 本次补记时正推进切换至 8 workers，是否全量完成以最终状态文件为准。主进程加载一次 nuScenes 表，Linux fork worker 继承只读对象，每个 token 仍调用同一生产 loader 并独立原子写 NPZ。已存在的正确缓存先读取并验证，不重复读取原始 PCD。开始加载元数据前即以原子写入的 `BUILDING` 覆盖旧状态，每 1,000 个主进程确认完成的 token 更新进度；失败写 `FAILED`，中断至少留下未完成状态。只有全部任务完成且没有显式 `--limit` 才写 `COMPLETE`，任何 limit 调用均保留 `LIMITED_SMOKE_ONLY`。并行失败时已有合法 NPZ 留作下次恢复使用，状态中的完成数以主进程已确认结果为准。

正式启动使用 `tools/launch_m3_h200_equivalent.sh`，不绕过其检查直接启动 torchrun。入口要求 `M3_PREFLIGHT_REPORT` 指向该精确 resolved config 对应的成功 `preflight_summary.json`：真实双卡至少完成 3 次 optimizer update，配置路径和小型配置文件摘要一致；并重新检查所选两个 H200 UUID 空闲、工作目录为空及正式参数。配置摘要只绑定短测与正式设置，不执行数据文件 SHA256 扫描。若缓存绑定或参数在短测后变化，需要验证最终正式配置，旧配置的 PASS 不能替代。

确认短测通过后，设置实际报告路径及可选 `M3_CONFIG` / `M3_PHYSICAL_GPUS`（GPU UUID），执行：

```bash
bash tools/launch_m3_h200_equivalent.sh --check
bash tools/launch_m3_h200_equivalent.sh
```

脚本固定 seed、deterministic、no-validate，并使用 `torch.distributed.run --standalone --nproc_per_node=2` 选择单机 rendezvous 端口，无需手工设置 `M3_MASTER_PORT`。本次补记时完整双卡短测仍在进行，以上是通过后的入口，不代表已取得 PASS 或已开始正式长训练。

不可添加 `--autoscale-lr`、改变物理 batch、把 warmup 改为 1,000，或将 M1 优化器 checkpoint 作为本次初始化。checkpoint 的 MMCV `meta.iter` 保留微步计数，`meta.equivalent_training.optimizer_updates_completed` 另记真正更新数；只接受同拓扑、完整 epoch、计数一致的 M3 恢复。
